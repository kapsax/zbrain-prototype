Simulate user:

Why this layout works

UX RATIONALE
1
Context switcher at the top of the sidebar

The pattern users already know from Slack, Notion and Linear. It always answers “where am I?” — a space or the Admin Console — and is the one control for moving between them. The hidden globe and gear icons are gone.

2
One sidebar carries all navigation

No second nav level in the content area — the header stays slim and the full screen belongs to the work. The sidebar collapses to an icon rail for even more room.

3
Admin Console: same shell, unmistakable identity

A blue accent strip, shield mark and “Account” kicker say you’re in account-level settings — without a jarring theme change. “Back to workspace” is always one click away.

4
Admin nav grouped by job-to-be-done

Spaces first (the admin’s core flow: create space → add members → attach policy), then Access · AI Resources · Governance · Account — instead of one flat list of 11 items.

5
Governance card pinned in the sidebar

The space’s policy and live token budget are always visible while working — builders see their limits before they hit them. Governance becomes transparent, not a surprise.

6
Role-aware navigation

The nav is filtered by what you can actually do. Builders get everything; a viewer sees only Observatory and Violations (marked view-only) — enough to use published solutions and see the governance affecting them, with nothing they can't act on. Configure Space and Monitor are gone.

7
My Account is reachable from wherever you are

It sits in the avatar menu for everyone — that’s the only route builders and viewers have, since they never see the Admin Console. Admins also get it listed under Account in the console, next to Billing, so it’s there when they’re already in settings. Both paths open the same page; personal settings stay clearly separate from the account-level ones.

8
Observatory = one consolidated command center

Usage, spend, model consumption and governance signals across all spaces in one place — with drill-downs (click a space bar, a health row, or a violation) instead of hopping space-by-space. It’s the admin’s landing page, because for an admin, watching the account is home.

9
One vocabulary at both altitudes

Observatory = watch, Governance = enforce — the same two words in the Admin Console and inside a space, with identical KPI + chart + table structure. Scope is carried by the context switcher and breadcrumb (“Admin Console / Observatory” vs “Human Resources / Observatory”), so users learn the dashboard once and read it everywhere.

10
Home speaks the dashboard language, but does a different job

Same KPI + card grammar as Observatory, yet Home answers “what’s here and what do I do next” (state and entry points) rather than “how is it trending” — so it has no time-range control. Every tile is a hand-off: solutions → Build, runs → Observatory, headroom and signals → Governance.

11
Governance is a conversation, not a wall

When a builder hits a policy limit — a model they can’t use, a budget that’s too small — they request the change from the exact screen where they hit it. The admin reviews it in one queue, and approving actually applies the change to that space. Without this loop, restrictive policies just push people to email and shadow tooling.

12
Requests start where the block happens

Build (models, APIs) and Prepare (data sources) both list every resource the space could use, with locked ones greyed and a “Request access” button in place. The builder never has to know what a policy is or where the admin lives — and the request arrives tagged with its origin, so the admin sees the context.

13
Approval is fulfillment, not a rubber stamp

“Approve” opens the work the admin actually has to do: for an API key — create new vs. reuse an account key, scope, expiry, rate limit, which policy to attach it to. For a budget — the admin can grant less than asked. The provisioned result (masked key, scope, expiry) is written back to the space and shown to the requester, so nothing happens off-platform.

14
Creating a space is a guided task, not a dialog

It takes over both panes: the steps live in the left rail (details → users → preview) and the active step fills the right, left-aligned. The rail doubles as progress and navigation — completed steps get a tick and stay clickable, later ones stay locked until the space has a name. Nothing is written until Publish space, and the preview step shows exactly what the policy will grant, so the admin sees the consequence before committing.

15
Editing reuses the same three steps

Edit opens the identical wizard pre-filled, so there’s nothing new to learn — only the last step differs: instead of a preview it shows a diff of what will change, old struck through and new in bold. Save stays disabled until something actually changes, and if a new policy removes a model the space was using, the step warns that solutions relying on it will stop running. The consequence is shown before the click, not discovered after.

16
Observatory summarises, Governance enumerates

The dashboard answers “is anything wrong?” — spend, runs, agent health, and the live governance feed — and nothing more. It shows only the 6 riskiest of 20 agents, because an account will have hundreds. Every exhaustive list lives behind a filtered log: Agent log for per-agent status, Audit & Activity for every violation, approval and trust change. Summary on top, detail one click down.

17
Every headline number opens its own log

Spend and Solution runs aren’t dead ends — clicking either opens the Usage log pre-set to that metric, where the same numbers can be regrouped by space, solution or model. Opening it from a space row scopes it to that space and switches the grouping to solutions, because that’s the next question you’d ask. One screen answers “where did it go?” at whatever altitude you need.

18
The space repeats the console's shape

Identical hierarchy, one altitude down: Observatory lands and summarises, then a Governance group holds the logs — Agent log, Usage log, Violations, Requests — exactly as the Admin Console does. Home is gone because Observatory answers the same question better. Learn the console once and the space needs no second explanation; only the scope and the permissions change.

19
Computed policy is a page, and every limit is actionable

It's a reference screen people read, compare and act from — so it takes the full pane rather than a dialog. Each value shows where it came from (policy default, this solution's allocation, or an approved exception), and anything that can be changed carries its own Request button that opens the ask pre-filled and pre-justified: budget on the budget row, a model on each locked model, a key on each unprovisioned connection, a policy change on every rule. Hitting a limit and asking for relief are the same gesture.

20
Carve-outs live inside the policy — and name what they cover

A grant floating outside the policy is a second access path nobody reviews, so a carve-out is a scoped override written into the policy itself. Every request must name the solution it's for, so approval can offer the narrowest correct grant by default — “Override scoped to Renewal forecaster” — with wider options stating exactly what they'd cover (“Sales · 5 solutions”, “base grants · 2 spaces”). Overrides expire, and can be revoked or promoted from the policy page.
